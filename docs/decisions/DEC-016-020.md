# Registro de decisiones DEC-016 a DEC-020

## DEC-016 — Supabase CLI local versionado y migrations-first

- **Fecha:** 2026-08-13
- **Sesión:** SESSION-20260813-008
- **Estado:** Accepted
- **Ámbito:** Backend local y persistencia
- **Reemplaza a:** ninguna decisión
- **Reemplazada por:** ninguna decisión
- **Rutas afectadas:** `implementation/package.json`, `implementation/pnpm-lock.yaml`, `implementation/supabase/`

### Contexto

El Technical Spike requiere una base Supabase/PostgreSQL reproducible antes de introducir PowerSync. No existe todavía un proyecto remoto ni datos de dominio, por lo que el esquema debe poder reconstruirse localmente y mantenerse bajo el límite `implementation/`.

### Decisión

El Supabase CLI oficial se distribuye como dependencia de desarrollo fijada del workspace (`supabase@2.114.0`) y los comandos locales se ejecutan mediante pnpm. La configuración queda exactamente en `implementation/supabase/`, con `config.toml` y migrations SQL versionadas, y estado temporal ignorado.

Los cambios PostgreSQL se realizan migrations-first: una migration ordenada es la fuente de verdad del esquema. `supabase db reset` reconstruye la base local aplicando migraciones y, si se introduce posteriormente, seed técnico versionado. No se enlaza ni crea ningún proyecto remoto en este flujo.

### Justificación

El CLI oficial admite instalarse como dependencia de proyecto y requiere Node.js 20 o superior en esa modalidad. El flujo oficial identifica `init`, `start`, migrations y `db reset` como camino local reproducible, y reserva `.temp/` y `.branches/` para estado no versionable.

### Consecuencias

- Docker Desktop o un runtime compatible con daemon accesible es un prerrequisito externo para ejecutar el stack.
- `config.toml` no contendrá secretos; cualquier secreto futuro se referenciará con `env()` desde un archivo ignorado.
- Las modificaciones realizadas en Studio solo son aceptables si se capturan y revisan en una migration antes de integrarse.
- La siguiente sesión puede usar la tabla técnica temporal, pero todavía debe configurar PowerSync de forma independiente.

### Alternativas consideradas

- Instalación global del CLI.
- Crear un proyecto Supabase remoto de forma automática.
- Mantener esquema solo en Studio o en SQL no versionado.

### Referencias

Instrucción explícita del propietario; `AGENTS.md`; [Supabase CLI Getting Started](https://supabase.com/docs/guides/local-development/cli/getting-started); [Supabase local development workflow](https://supabase.com/docs/guides/local-development/cli-workflows); [Supabase CLI reference](https://supabase.com/docs/reference/cli/getting-started); SESSION-20260813-008.

## DEC-017 — PowerSync Web con SQLite administrado y limpieza por identidad

- **Fecha:** 2026-08-13
- **Sesión:** SESSION-20260813-009
- **Estado:** Accepted
- **Ámbito:** Persistencia y sincronización del cliente web
- **Reemplaza a:** ninguna decisión
- **Reemplazada por:** ninguna decisión
- **Rutas afectadas:** `implementation/apps/web/src/lib/powersync/`, `implementation/powersync/`, `implementation/supabase/migrations/`

### Contexto

El cliente PWA debe leer y escribir localmente en SQLite y sincronizar con Supabase sin convertir APIs de almacenamiento del navegador en una base empresarial paralela. El cambio de usuario debe impedir que una identidad vea datos locales de la anterior.

### Decisión

El cliente web usa el SDK oficial `@powersync/web`, SQLite/WASM mediante `@journeyapps/wa-sqlite` y `@powersync/react` para reactividad. PowerSync administra el archivo SQLite y su VFS. `spike_records` es la única tabla local sincronizada; las descargas se filtran con Sync Streams edición 3 y los uploads llegan a Supabase mediante el cliente existente y RLS.

El ciclo de SQLite espera la restauración de Auth. Un marcador local no empresarial con el UUID de la última identidad permite conservar SQLite al reiniciar únicamente cuando se restablece esa misma identidad. Si el marcador falta, la identidad cambia o se ejecuta logout, el cliente llama `disconnectAndClear()` antes de continuar; la UI nunca filtra datos viejos como sustituto de limpiar la base.

### Justificación

Es el flujo vigente documentado por PowerSync para React/Web, permite escritura local inmediata, cola de uploads y sincronización de retorno. `disconnectAndClear()` es el mecanismo explícitamente recomendado por el SDK para logout.

### Consecuencias

- PowerSync Cloud Development y su Instance URL son prerrequisitos externos para sincronizar.
- Supabase RLS sigue siendo la autoridad sobre escrituras; Sync Streams solo gobierna descargas.
- El spike limita publicación, schema local, connector y uploads a `spike_records`.
- La persistencia tras cerrar/reabrir y la reconexión offline requieren validación manual end-to-end; las pruebas automatizadas ya cubren la conservación para la misma identidad y la limpieza ante identidad desconocida, cambio o logout.

### Alternativas consideradas

- Persistencia manual en IndexedDB o localStorage.
- Filtrar la UI sin limpiar SQLite al cambiar de usuario.
- Usar Sync Streams como reemplazo de RLS.

### Referencias

Instrucción explícita del propietario; DEC-002; DEC-003; DEC-004; [PowerSync JavaScript Web SDK](https://docs.powersync.com/client-sdks/reference/javascript-web); [Supabase + PowerSync](https://docs.powersync.com/integrations/supabase/guide); [Sync Streams](https://docs.powersync.com/sync/streams/overview); SESSION-20260813-009.

## DEC-018 — Perfil único con rol inicial y resolución segura de empresa

- **Fecha:** 2026-08-13
- **Sesión:** SESSION-20260813-010
- **Estado:** Accepted
- **Ámbito:** Identidad, autorización y aislamiento empresarial
- **Reemplaza a:** ninguna decisión
- **Reemplazada por:** ninguna decisión
- **Rutas afectadas:** `implementation/supabase/migrations/20260813170000_create_identity_company_foundation.sql`

### Contexto

R&T SITRAM SAC inicia como una sola empresa operativa, pero los datos de producto deben tener un límite empresarial explícito. Los roles iniciales están definidos y cada usuario tendrá un único rol; crear RBAC genérico, tablas de permisos o roles por empresa no aporta valor al alcance actual.

### Decisión

`profiles` conserva una relación 1:1 con `auth.users`, un `company_id` y un único `role` de enum PostgreSQL: `management`, `administration`, `driver` o `accounting`. Las credenciales no se duplican.

Las políticas RLS resuelven empresa y rol con funciones `security definer` sin parámetros (`current_company_id()` y `current_app_role()`). Las funciones solo devuelven valores del perfil activo de `auth.uid()` y no aceptan IDs provenientes del cliente. Management y administration pueden leer perfiles de su propia empresa; driver y accounting solo su propio perfil en esta etapa.

### Consecuencias

- Toda tabla empresarial futura debe incluir y proteger `company_id` con la misma resolución de identidad.
- El frontend no puede crear empresas, perfiles ni alterar `company_id` o `role`.
- Al necesitar múltiples roles o permisos granulares, se evaluará una evolución explícita del modelo; no se anticipa ahora.
- Las funciones evitan autorreferencias RLS sobre `profiles` y se conceden únicamente a `authenticated`.

### Alternativas consideradas

- Tablas `roles`, `user_roles` y permisos N:M desde el inicio.
- Resolver `company_id` recibido por el frontend.
- Consultar `profiles` directamente dentro de sus propias policies.

### Referencias

Instrucción explícita del propietario; DEC-004; `docs/05_arquitectura_informacion_modelo_datos.md`; `docs/08_plan_maestro_implementacion.md`; [Supabase Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security); SESSION-20260813-010.

## DEC-019 — Sincronización de producto y recuperación explícita de colas

- **Fecha:** 2026-08-16
- **Sesión:** SESSION-20260813-010
- **Estado:** Accepted
- **Ámbito:** Sincronización y operación offline
- **Reemplaza a:** alcance experimental de DEC-017
- **Reemplazada por:** ninguna decisión
- **Rutas afectadas:** `implementation/powersync/`, `implementation/apps/web/src/lib/powersync/`, `implementation/apps/web/src/features/driver-ui/`

### Contexto y decisión

El producto requiere que el flujo esencial del conductor funcione sin conexión sin presentar estados locales como confirmados por el servidor. Los Sync Streams de producción se limitan por perfil y empresa activos, rol y asignación vigente. Todas las transiciones del conductor se escriben primero en SQLite y se aplican en orden mediante comandos idempotentes.

Una mutación terminal se separa en una cola local auditable para no bloquear las siguientes. Las evidencias agotadas quedan disponibles para reintento o descarte confirmado; el descarte elimina solo el archivo local y conserva el registro empresarial. El logout se bloquea mientras existan operaciones o evidencias sin resolver.

### Consecuencias

- RLS sigue autorizando escrituras y Sync Streams filtra descargas.
- Management y administration disponen de lectura local parcial; sus comandos siguen siendo online-only.
- La validación automatizada no reemplaza la prueba física en Android con corte real de red.

## DEC-020 — Comandos autoritativos e inmutabilidad financiera

- **Fecha:** 2026-08-16
- **Sesión:** SESSION-20260813-010
- **Estado:** Accepted
- **Ámbito:** Operación, finanzas y auditoría
- **Reemplaza a:** ninguna decisión
- **Reemplazada por:** ninguna decisión
- **Rutas afectadas:** `implementation/supabase/migrations/`, `implementation/apps/web/src/features/admin-ui/`

### Contexto y decisión

Las transiciones operativas, revisiones de gasto, adelantos, facturación y cierres no se autorizan mediante escrituras arbitrarias del cliente. Se exponen comandos PostgreSQL pequeños, ligados a `auth.uid()`, empresa y rol. Crear viaje y carga es atómico; los reintentos financieros comparan actor y payload completo.

Una rendición solo cierra con gastos resueltos y evidencia explícita de devolución o reembolso cuando el saldo no es cero. El cierre vuelve inmutables los gastos del viaje; una reapertura auditada habilita cambios posteriores. Los archivos permanecen privados y asociados por metadata empresarial.

### Consecuencias

- Los RPC públicos tienen una allowlist explícita para `authenticated`; `anon`, `PUBLIC` y `service_role` no heredan ejecución accidental.
- Las invariantes se prueban con pgTAP remoto dentro de transacciones revertidas.
- Nuevas operaciones sensibles deben ampliar comandos y pruebas, no grants genéricos de tabla.
