# Registro de decisiones DEC-001 a DEC-005

## DEC-001 — PWA como cliente principal

- **Fecha:** 2026-08-12
- **Sesión:** SESSION-20260812-001
- **Estado:** Accepted
- **Ámbito:** Cliente
- **Reemplaza a:** ninguno
- **Reemplazada por:** ninguno
- **Rutas afectadas:** `implementation/apps/web/`

### Contexto

Administración, gerencia y conductores requieren una experiencia única en dispositivos de escritorio y móviles, incluso sin conectividad.

### Decisión

El cliente principal será una PWA responsive.

### Justificación

Una única base de código cubre los perfiles previstos y permite instalación y app shell offline.

### Alternativas consideradas

Aplicaciones nativas Android/iOS independientes, web separada y escritorio separado.

### Consecuencias

La implementación deberá incluir las capacidades PWA y validar su comportamiento en los dispositivos objetivo.

### Referencias

`docs/07_arquitectura_tecnica_sistema.md` §§2–5, 113, 218–222; `docs/08_plan_maestro_implementacion.md` §§9, 30.

## DEC-002 — Arquitectura offline-first

- **Fecha:** 2026-08-12
- **Sesión:** SESSION-20260812-001
- **Estado:** Accepted
- **Ámbito:** Persistencia
- **Reemplaza a:** ninguno
- **Reemplazada por:** ninguno
- **Rutas afectadas:** `implementation/apps/web/`, `implementation/packages/domain/`, `implementation/powersync/`

### Contexto

Los conductores deben continuar la operación en carretera sin señal y los registros no pueden perderse al cerrar la aplicación.

### Decisión

La aplicación trabajará contra datos locales persistentes y sincronizará cuando exista conectividad.

### Justificación

El flujo local primero actualiza la interfaz de inmediato y evita depender del servidor para cada interacción cotidiana.

### Alternativas consideradas

Formularios temporales en memoria o un flujo pantalla–internet–servidor para toda operación.

### Consecuencias

Persistencia, sincronización y pruebas offline son requisitos de primer nivel; el service worker no sustituye la base empresarial local.

### Referencias

`docs/07_arquitectura_tecnica_sistema.md` §§4–5, 206–207, 212, 214–215, 222; `docs/08_plan_maestro_implementacion.md` §§1, 13–15, 54.

## DEC-003 — PowerSync para sincronización

- **Fecha:** 2026-08-12
- **Sesión:** SESSION-20260812-001
- **Estado:** Accepted
- **Ámbito:** Sincronización
- **Reemplaza a:** ninguno
- **Reemplazada por:** ninguno
- **Rutas afectadas:** `implementation/powersync/`, `implementation/apps/web/`

### Contexto

El modelo offline-first necesita sincronización de datos locales y una cola de escrituras para los cambios realizados sin conexión.

### Decisión

Se usará PowerSync para sincronizar datos entre SQLite local y el backend.

### Justificación

La arquitectura fuente define sus streams, descarga de cambios y cola de escrituras, con integración para Supabase.

### Alternativas consideradas

Sincronización ad hoc implementada por la aplicación.

### Consecuencias

Se deberá validar empíricamente la compatibilidad web, cierre de PWA, conflictos y tamaño del dataset local durante el spike.

### Referencias

`docs/07_arquitectura_tecnica_sistema.md` §§2, 206–207, 215, 218, 222; `docs/08_plan_maestro_implementacion.md` §§9, 15, 29.

## DEC-004 — Supabase/PostgreSQL como backend

- **Fecha:** 2026-08-12
- **Sesión:** SESSION-20260812-001
- **Estado:** Accepted
- **Ámbito:** Backend
- **Reemplaza a:** ninguno
- **Reemplazada por:** ninguno
- **Rutas afectadas:** `implementation/supabase/`, `implementation/powersync/`

### Contexto

Los datos empresariales, seguridad, dinero, cierres y auditoría requieren una fuente central autoritativa.

### Decisión

Supabase con PostgreSQL será el backend y la base central autoritativa, con Auth, Storage, RLS y lógica server-side previstos por la arquitectura.

### Justificación

PostgreSQL consolida la verdad empresarial y Supabase aporta los servicios administrados requeridos.

### Alternativas consideradas

Backend no definido o lógica sensible exclusivamente en el cliente.

### Consecuencias

Las operaciones sensibles se validarán y consolidarán en el backend; las reglas definitivas de RLS se validarán durante el spike.

### Referencias

`docs/07_arquitectura_tecnica_sistema.md` §§2, 42, 206, 218–219, 222; `docs/08_plan_maestro_implementacion.md` §§9, 24–29.

## DEC-005 — UUID como identificadores

- **Fecha:** 2026-08-12
- **Sesión:** SESSION-20260812-001
- **Estado:** Accepted
- **Ámbito:** Datos
- **Reemplaza a:** ninguno
- **Reemplazada por:** ninguno
- **Rutas afectadas:** `implementation/packages/domain/`, `implementation/supabase/migrations/`, `implementation/powersync/schema/`

### Contexto

Los registros pueden originarse offline y deben poder recibir un identificador antes de sincronizar.

### Decisión

Los registros creables offline usarán UUID generables en el cliente como identificador principal.

### Justificación

Evita depender de secuencias centralizadas como `SELECT MAX(id) + 1` al crear datos sin conexión.

### Alternativas consideradas

Identificadores secuenciales asignados por consulta al servidor.

### Consecuencias

Los contratos de dominio, esquema local y migraciones deberán conservar UUID como ID principal de estas entidades.

### Referencias

`docs/07_arquitectura_tecnica_sistema.md` §23, §218; `docs/08_plan_maestro_implementacion.md` §9.
