# Registro de decisiones DEC-011 a DEC-015

## DEC-011 — Raíz Git independiente del proyecto

- **Fecha:** 2026-08-12
- **Sesión:** SESSION-20260812-003
- **Estado:** Accepted
- **Ámbito:** Gobierno
- **Reemplaza a:** ninguno
- **Reemplazada por:** ninguno
- **Rutas afectadas:** `.git/`, `.gitignore`, `docs/decisions/`, `docs/sessions/`, `docs/audits/`

### Contexto

La carpeta del proyecto heredaba la raíz Git de `C:/Users/Ruben J`. Esto mezclaba cambios externos con el estado, diff y validaciones del proyecto, impidiendo un aislamiento fiable para auditorías y sesiones.

### Decisión

El directorio `C:/Users/Ruben J/Documents/R&T SITRAM SAC - Project` tendrá una raíz Git independiente, inicializada localmente. El repositorio Git padre permanece fuera del alcance y sin modificaciones.

### Justificación

Una raíz propia limita el control de cambios, validaciones y futuros commits a los archivos del proyecto, preservando la trazabilidad y la seguridad operativa del gobierno del repositorio.

### Alternativas consideradas

- Continuar usando el repositorio Git padre y filtrar manualmente cada comando.
- Mover el proyecto fuera del árbol del repositorio padre.

### Consecuencias

Los comandos Git ejecutados desde el proyecto operarán sobre su propia raíz. Se añade un `.gitignore` para dependencias, secretos, artefactos locales y cachés futuras, sin ignorar documentación, gobierno, migraciones ni implementación versionable. No se creó ningún commit automático.

### Referencias

Instrucción explícita del usuario de gobierno; `AGENTS.md`; `docs/audits/00_index.md` PRE-001; `SESSION-20260812-003`.

## DEC-012 — Validación Just-in-Time en lugar de auditoría documental exhaustiva previa

- **Fecha:** 2026-08-12
- **Sesión:** SESSION-20260812-005
- **Estado:** Accepted
- **Ámbito:** Gobierno de desarrollo
- **Reemplaza a:** ninguna decisión
- **Reemplazada por:** ninguna
- **Rutas afectadas:** `docs/audits/00_index.md`, `docs/decisions/`, `docs/sessions/`

### Contexto

La campaña de auditoría documental exhaustiva generó un coste de coordinación desproporcionado y convertía incertidumbres de dominio no relacionadas en bloqueos de la fundación técnica. AUD-01 conserva riesgos materiales, pero estos no impiden por sí mismos el Technical Spike offline-first.

### Decisión

La documentación existente continúa como fuente de verdad provisional. Las dudas se resolverán cuando sean materialmente relevantes para una sesión de implementación concreta. AUD-02 a AUD-11 dejan de ser gates globales obligatorios, no se ejecutarán automáticamente y podrán reutilizarse parcialmente como checklists Just-in-Time. Los riesgos conocidos permanecen documentados.

### Justificación

Permite validar decisiones con evidencia de implementación sin tratar incertidumbres ajenas al alcance como bloqueadores globales.

### Consecuencias

Positivas:

- Desarrollo más rápido y menor consumo de contexto.
- Decisiones respaldadas por evidencia técnica empírica.
- Menos burocracia y sesiones pequeñas verificables.

Riesgos:

- Algunas decisiones de dominio pueden requerir refactor futuro.

Mitigación:

- Verticales pequeñas, migraciones controladas, pruebas, DEC y logs de sesión.
- No implementar partes ambiguas hasta resolver el bloqueo concreto.
- Investigación externa focalizada para OCR, GPS y reutilización open source cuando corresponda.

### Alternativas consideradas

- Completar AUD-02 a AUD-11 antes de cualquier desarrollo.
- Ignorar los hallazgos de AUD-01.

### Referencias

Instrucción explícita del propietario; `AGENTS.md`; `docs/audits/00_index.md`; `docs/audits/01_negocio_dominio.md`; `SESSION-20260812-005`.

## DEC-013 — Toolchain base del workspace frontend

- **Fecha:** 2026-08-12
- **Sesión:** SESSION-20260812-006
- **Estado:** Accepted
- **Ámbito:** Tooling de implementación
- **Reemplaza a:** ninguna decisión
- **Reemplazada por:** ninguna
- **Rutas afectadas:** `implementation/package.json`, `implementation/pnpm-workspace.yaml`, `implementation/pnpm-lock.yaml`, `implementation/apps/web/`, `implementation/packages/shared/`

### Contexto

La primera sesión con autorización para modificar `implementation/` requiere un cliente web reproducible, tipado y extensible sin introducir funcionalidades de negocio ni adelantar la demostración offline. La arquitectura Accepted ya fija React, TypeScript, Vite, PWA, Supabase y PowerSync; faltaba fijar el runtime, el gestor de paquetes, la topología de workspace y el tooling mínimo compatible.

### Decisión

`implementation/` usará Node.js 24 LTS (`>=24.0.0 <25`) y pnpm 11.19.x (`>=11.19.0 <12`) como gestor único. Se organiza como workspace pnpm con los patrones `apps/*` y `packages/*`.

La aplicación inicial es `@rt-sitram/web`, con React 19.2.8, TypeScript 6.0.2 y Vite 8.2.1. El lint y el formato se realizan con Oxlint y Oxfmt; Vitest se usa para la prueba automatizada mínima. `@rt-sitram/shared` contiene solo una utilidad técnica no perteneciente al dominio, para validar la resolución entre workspaces.

El lockfile `pnpm-lock.yaml` es parte obligatoria del workspace. PowerSync, Supabase y la infraestructura PWA no se instalan ni configuran todavía.

### Justificación

Node 24 es una línea LTS vigente y el entorno disponible ya la ejecuta. La guía oficial de Vite requiere Node 20.19+ o 22.12+ y su plantilla React/TypeScript vigente usa React 19.2, TypeScript 6 y Vite 8. PowerSync Web declara compatibilidad con React y otras SPA, pero exige APIs de navegador, lo que encaja con un cliente Vite sin SSR. Supabase JavaScript se distribuye por pnpm y no introduce una restricción material para este cliente web.

pnpm y su lockfile permiten un workspace simple y reproducible sin incorporar herramientas de orquestación adicionales. El tooling seleccionado cubre typecheck, lint, formato y pruebas con coste inicial acotado.

### Alternativas consideradas

- npm sin workspace pnpm ni lockfile pnpm.
- Yarn, no disponible en el entorno y sin una ventaja concreta para este repositorio.
- Instalar desde ahora SDKs, credenciales o configuración de Supabase, PowerSync y PWA.
- Crear paquetes de dominio ficticios para completar el árbol.

### Consecuencias

- Todos los comandos de desarrollo se ejecutan desde `implementation/` con pnpm.
- Los futuros paquetes de dominio y UI podrán incorporarse bajo `packages/*` y consumirse con dependencias `workspace:*`.
- Cualquier cambio de major del runtime, gestor de paquetes, topología de workspace o herramienta base requiere reevaluación y, si es duradero, una DEC.
- La siguiente sesión puede preparar PWA y Supabase/Auth sin confundir el caché del shell con la futura SQLite empresarial.

### Referencias

Instrucción explícita del usuario; `AGENTS.md`; `docs/07_arquitectura_tecnica_sistema.md` (secciones 3–7); `docs/08_plan_maestro_implementacion.md` (estructura inicial, Fase 1 y Épicas 2.6–2.7); [Node.js Releases](https://nodejs.org/en/about/previous-releases); [Vite Getting Started](https://vite.dev/guide/); [Vite React TypeScript template](https://github.com/vitejs/vite/tree/main/packages/create-vite/template-react-ts); [React Versions](https://react.dev/versions); [TypeScript 6.0](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html); [PowerSync JavaScript Web SDK](https://docs.powersync.com/client-sdks/reference/javascript-web); [Supabase JavaScript installation](https://supabase.com/docs/reference/javascript/installing); [PWA installation](https://web.dev/learn/pwa/installation).

## DEC-014 — Shell PWA estándar sin integración Vite adicional

- **Fecha:** 2026-08-13
- **Sesión:** SESSION-20260813-007
- **Estado:** Accepted
- **Ámbito:** Cliente PWA
- **Reemplaza a:** ninguna decisión
- **Reemplazada por:** ninguna decisión
- **Rutas afectadas:** `implementation/apps/web/index.html`, `implementation/apps/web/public/`, `implementation/apps/web/src/lib/pwa/`, `implementation/apps/web/src/main.tsx`

### Contexto

La PWA mínima del Technical Spike requiere manifest, iconos, registro y caché de app shell, sin anticipar el almacenamiento empresarial. La comprobación Just-in-Time de `vite-plugin-pwa` muestra que su rango de `peerDependencies` publicado no incluye Vite 8, aunque exista trabajo de compatibilidad en curso. Forzar dicha combinación incorporaría una advertencia de compatibilidad y dependencias Workbox no necesarias para este shell reducido.

### Decisión

Se usa un Web App Manifest, iconos PNG y un service worker estándar propio, pequeño y auditable. En producción registra `/sw.js`, precachea únicamente HTML, JavaScript, CSS, manifest e iconos de la aplicación, y usa una estrategia network-first con fallback a ese caché para el shell. No se añade una dependencia PWA.

### Justificación

La implementación satisface el requisito actual de PWA instalable y reapertura offline sin acoplar el workspace a una integración que aún no declara Vite 8 como peer compatible. El alcance limitado permite revisar explícitamente todas las rutas cacheadas y preserva la separación entre app shell y futuros datos SQLite/PowerSync.

### Alternativas consideradas

- Instalar `vite-plugin-pwa` con una resolución/override de peer dependency para Vite 8.
- Usar Workbox o un service worker manual con runtime caching de datos.
- No implementar caché hasta la sesión de SQLite/PowerSync.

### Consecuencias

- Las actualizaciones de assets del shell requieren actualizar `CACHE_NAME` y sus rutas previsibles si cambia la salida del build.
- Cache Storage no es fuente de datos empresariales ni almacena respuestas de Supabase, PowerSync o documentos.
- Una futura adopción de una integración PWA mantenida se reevalúa cuando declare soporte de Vite 8 y aporte una ventaja material.

### Referencias

Instrucción explícita del usuario; `AGENTS.md`; `docs/07_arquitectura_tecnica_sistema.md` secciones 3–5 y 8; [vite-plugin-pwa repository](https://github.com/vite-pwa/vite-plugin-pwa); [issue de compatibilidad Vite 8](https://github.com/vite-pwa/vite-plugin-pwa/issues/923); [Chrome installability manifest requirements](https://developer.chrome.com/docs/lighthouse/pwa/installable-manifest); [web.dev manifest guidance](https://web.dev/articles/add-manifest).

## DEC-015 — Cliente Supabase SPA encapsulado y Auth local por dispositivo

- **Fecha:** 2026-08-13
- **Sesión:** SESSION-20260813-007
- **Estado:** Accepted
- **Ámbito:** Identidad de cliente
- **Reemplaza a:** ninguna decisión
- **Reemplazada por:** ninguna decisión
- **Rutas afectadas:** `implementation/apps/web/src/lib/supabase/`, `implementation/apps/web/src/features/auth/`, `implementation/apps/web/.env.example`

### Contexto

El cliente actual es una SPA React/Vite, sin SSR ni cookies de servidor. El Technical Spike solo necesita identidad email/password, restauración de sesión, observación de cambios y logout sin afectar otros dispositivos.

### Decisión

Se instala `@supabase/supabase-js` 2.110.8 y se crea un único cliente browser en `src/lib/supabase/client.ts`, condicionado por configuración tipada. Solo consume `VITE_SUPABASE_URL` y `VITE_SUPABASE_PUBLISHABLE_KEY`; no existe fallback de credenciales. Auth usa un provider/hook React mínimo con estados `INITIALIZING`, `AUTHENTICATED` y `UNAUTHENTICATED`, `getSession`, `onAuthStateChange` y limpieza de suscripción. El logout usa `signOut({ scope: "local" })`.

### Justificación

Supabase recomienda el cliente base para navegador cuando no se requieren cookies ni SSR. La persistencia soportada de la sesión queda activa para la SPA; un scope local satisface la prueba sin revocar innecesariamente sesiones en otros dispositivos. La configuración visible en Vite solo admite una publishable key, que es pública por diseño.

### Alternativas consideradas

- Crear clientes `createClient()` dentro de componentes React.
- Introducir `@supabase/ssr`, cookies o un framework SSR.
- Usar una anon key nueva en lugar de publishable key.
- Usar logout global, que por defecto puede cerrar todas las sesiones del usuario.

### Consecuencias

- `VITE_*` se considera público; secret keys y service-role nunca entran en el bundle.
- La UI puede presentar una sesión local restaurada sin afirmar verificación de identidad remota ni autorización RLS mientras no haya red.
- No se implementan signup público, roles, perfiles, RLS ni operaciones de dominio.

### Referencias

Instrucción explícita del usuario; [Supabase package selection](https://supabase.com/docs/guides/auth/choosing-a-server-package); [Supabase JavaScript Auth](https://supabase.com/docs/reference/javascript/auth); [React quickstart](https://supabase.com/docs/guides/auth/quickstarts/react); [API keys](https://supabase.com/docs/guides/getting-started/api-keys); [onAuthStateChange](https://supabase.com/docs/reference/javascript/auth-onauthstatechange); [signOut](https://supabase.com/docs/reference/javascript/auth-signout); [@supabase/supabase-js 2.110.8](https://www.npmjs.com/package/@supabase/supabase-js).
